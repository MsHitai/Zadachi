# Бинарный поиск

Примеры — из решений этого репозитория (каталог — [TASKS.md](../TASKS.md)).

Главная мысль: бинарный поиск — это не про массив, а про **монотонное условие**. Есть ряд позиций, для которых условие сначала ложно, а с какого-то места всегда истинно: `нет нет нет да да да`. Бинарный поиск находит первое «да».

---

## 1. Как узнать задачу

| Что написано в условии | Подход |
|---|---|
| Массив отсортирован, найти элемент или позицию | классический бинпоиск |
| Требуется O(log n) | бинпоиск |
| «Первая / последняя позиция элемента», «сколько элементов меньше x» | lower bound / upper bound |
| «**Минимальное** X, при котором успеваем / хватает / помещается» | бинпоиск по ответу |
| «**Максимальное** X, при котором всё ещё можно» | бинпоиск по ответу |
| «Минимизировать максимум», «максимизировать минимум» | бинпоиск по ответу |
| Отсортированный массив сдвинут по кругу | бинпоиск с проверкой, какая половина отсортирована |
| Ответ — число до 10⁹ и больше, а проверить конкретный ответ легко | бинпоиск по ответу |

Проверочный вопрос для бинпоиска по ответу: **если X подходит, подходит ли X + 1?** (или X − 1). Если да — условие монотонно, бинпоиск применим.

## 2. Один шаблон на все случаи

**Соглашение:** ищем первую позицию, где условие истинно. Ответ лежит в `[left, right]`, причём `right` — либо заведомо подходящая позиция, либо «за концом», что означает «ответа нет».

```java
int left = 0, right = n;           // right = n: подходящей позиции может не быть
while (left < right) {
    int mid = left + (right - left) / 2;
    if (подходит(mid)) {
        right = mid;               // mid может быть ответом — оставляем
    } else {
        left = mid + 1;            // mid точно не ответ — выбрасываем
    }
}
return left;                       // первое «да»; n, если его нет
```

Всё в шаблоне выводится, а не запоминается:

- **`right = mid`, а не `mid - 1`**: `mid` подошёл, он может оказаться первым подходящим, выбрасывать его нельзя.
- **`left = mid + 1`**: `mid` не подошёл, ответом он быть не может.
- **`left < right`, а не `<=`**: цикл заканчивается, когда кандидат остался один, то есть `left == right`.
- **Цикл не зависнет**: `mid` округляется вниз, поэтому `mid < right` всегда, и `right = mid` уменьшает отрезок.

**Правило про зависание.** Если пишете `left = mid` (без `+ 1`), середину надо округлять вверх: `mid = left + (right - left + 1) / 2`. Иначе при `right == left + 1` получится `mid == left` и вечный цикл. Проще этого избегать и всегда искать «первое да».

**Как искать «последнее да»** (максимальное X, при котором можно). Перевернуть условие: найти первое «нет» тем же шаблоном и вычесть единицу.

**`mid = left + (right - left) / 2`**, а не `(left + right) / 2`: сумма может переполнить `int`.

### Lower bound и upper bound

- Первая позиция, где `nums[i] >= x` — условие `nums[mid] >= x`.
- Первая позиция, где `nums[i] > x` — условие `nums[mid] > x`.
- Количество элементов, равных x: вторая минус первая.
- Последняя позиция x: вторая минус один.

Примеры из репозитория:

- [SearchInsertPosition](../src/leetcode/challenges/SearchInsertPosition.java) (LC 35) — ровно этот шаблон: `right = nums.length`, потому что элемент может вставляться в самый конец.
- [TwoBicycles](../src/ya/algorithm_course/third_sprint_sort/TwoBicycles.java) (≈LC 34) — тоже первая позиция со значением ≥ x, но записано в другом соглашении (см. ниже): `left <= right` и переменная `result`.

### Вариант с `left <= right`

Часто пишут другой шаблон: отрезок `[left, right]` с `right = n - 1`, цикл `while (left <= right)`, сдвиги `mid + 1` и `mid - 1`. Он тоже верный, но это **другое соглашение**: здесь отрезок — множество ещё не проверенных элементов, и он может стать пустым.

- Для точного поиска при совпадении сразу `return mid`.
- Для поиска первого подходящего найденный `mid` запоминают в отдельной переменной (`result = mid`) и продолжают искать левее: `right = mid - 1`. Так сделано в [TwoBicycles](../src/ya/algorithm_course/third_sprint_sort/TwoBicycles.java). В [MockInterviewTask](../src/ya/algorithm_course/MockInterviewTask.java) переменной нет: после цикла первое подходящее значение лежит в `left`.

В репозитории, таким образом, встречаются оба соглашения. Для новых решений стоит выбрать одно и писать только его.

Ошибки на единицу возникают при смешивании: `left < right` вместе с `right = mid - 1` теряет элементы, `left <= right` вместе с `right = mid` зависает.

## 3. Бинарный поиск по ответу

Ищем не индекс в массиве, а само число-ответ. Три вопроса:

1. **В каких границах лежит ответ?** Минимально и максимально возможное значение.
2. **Монотонно ли условие?** Если X подходит, то и всё, что больше (или меньше), подходит.
3. **Как проверить конкретный X?** Обычно жадный проход за O(n).

Итоговая сложность — O(n · log(диапазон)).

Примеры из репозитория:

- [KokoEatingBananas](../src/leetcode/challenges/KokoEatingBananas.java) (LC 875). Ответ — скорость от 1 до размера самой большой кучи. Если со скоростью X успеваем, то с X + 1 тем более. Проверка — сумма часов по кучам. Округление вверх без дробей: `(pile - 1) / speed + 1`. Для верхней границы достаточно максимума, сортировать массив не обязательно.
- [MockInterviewTask](../src/ya/algorithm_course/MockInterviewTask.java) (LC 410). Ответ — наибольшая сумма части, от максимального элемента до суммы всех. Проверка: жадно набираем части, пока сумма не превысит X, и считаем, сколько частей получилось.

Границы подбираем так, чтобы `right` заведомо подходил: тогда шаблон из раздела 2 работает без изменений и ответ всегда существует.

## 4. Сдвинутый отсортированный массив

[SearchInBrokenArray](../src/ya/algorithm_course/third_sprint_sort/final_test/SearchInBrokenArray.java) (≈LC 33). Массив разрезали и поменяли части местами.

Ключевое наблюдение: после деления пополам **хотя бы одна половина отсортирована**. Какая — видно по сравнению `arr[left] <= arr[mid]`. Для отсортированной половины легко проверить, лежит ли в ней искомое значение. Если лежит — идём туда, иначе в другую.

## 5. Типичные ошибки

- Смешаны два соглашения (см. раздел 2).
- `left = mid` при округлении вниз — вечный цикл.
- `right = n - 1`, когда ответом может быть позиция `n`.
- Переполнение: в `mid`, в сумме при проверке (нужен `long`), в верхней границе ответа.
- В бинпоиске по ответу нижняя граница 0 приводит к делению на ноль.
- Условие на самом деле не монотонно — бинпоиск вернёт что-то, но не ответ.

## 6. С чем не путать

| Выглядит как | Но на самом деле | Как отличить |
|---|---|---|
| Бинпоиск по массиву | хеш-мапа | массив не отсортирован, а сортировка не окупается |
| Бинпоиск | два указателя | ищем пару в отсортированном массиве: O(n) вместо O(n log n) |
| ДП: «минимизировать максимум» | бинпоиск по ответу | конкретный ответ легко проверить жадно |
| Перебор ответа от 1 до max | бинпоиск по ответу | условие монотонно, диапазон большой |

Бинпоиск бывает частью другого решения: в [LongestSubSequence](../src/stepik/algorithms/LongestSubSequence.java) (≈LC 300) он ищет место в массиве «хвостов» и даёт O(n log n) вместо O(n²).
