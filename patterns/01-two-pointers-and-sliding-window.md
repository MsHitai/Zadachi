# Два указателя и скользящее окно

Заметка не про решения, а про три вещи: как узнать задачу, что означают указатели и как из этого вывести код. Примеры взяты из решений этого репозитория (каталог — [TASKS.md](../TASKS.md)).

Главная мысль всей заметки: **условие цикла не запоминают, а выводят из того, что означают указатели**. Сначала одной фразой формулируем смысл указателей (инвариант), пишем его комментарием, и только потом пишем код.

---

## 1. Как узнать задачу

| Что написано в условии | Подход |
|---|---|
| Массив отсортирован, нужно найти пару (сумма, разность, ближайшие) | два указателя навстречу |
| Палиндром, «симметрично», «развернуть», «с обоих концов» | два указателя навстречу |
| «In-place», «O(1) памяти», убрать или переставить элементы, сохранив порядок | указатель чтения и указатель записи |
| Два отсортированных массива или две строки, нужно слить, сравнить, сопоставить | по указателю на каждый массив |
| Разложить элементы на три группы за один проход | три указателя (голландский флаг) |
| **Непрерывный** подмассив или подстрока + «самый длинный / самый короткий / сколько» + условие на содержимое | скользящее окно |
| Подмассив или подстрока фиксированной длины k | окно фиксированного размера |

Два вопроса, которые отсекают лишнее:

1. **Нужен непрерывный кусок или можно выбирать элементы с пропусками?** Окно работает только для непрерывного куска (subarray, substring). Если элементы можно пропускать (subsequence), это не окно.
2. **Условие монотонно?** Окно работает, когда добавление элемента справа может только ухудшить окно (или только улучшить), а удаление слева — только наоборот. Сумма положительных чисел монотонна. Сумма с отрицательными числами — нет.

Подсказка из ограничений: если n до 10⁵ и перебор всех пар O(n²) не проходит, а ответ — пара или отрезок, почти всегда это два указателя, окно или хеш-мапа.

## 2. Два указателя

Общее у всех разновидностей: каждый указатель движется только в одну сторону, поэтому суммарно шагов не больше 2n и сложность O(n).

### 2.1. Навстречу друг другу

**Сигнал:** отсортированный массив и пара, либо симметрия (палиндром).

**Смысл указателей:** всё, что левее `left` и правее `right`, уже рассмотрено и отброшено. Ответ, если он есть, лежит внутри `[left, right]`.

```java
int left = 0, right = n - 1;
while (left < right) {
    if (нашли ответ) return ...;
    if (нужно больше) left++;
    else right--;
}
```

**Какой указатель двигать.** Двигаем тот, который уже не может дать ответ лучше. В Two Sum II (LC 167) при `nums[left] + nums[right] < target` число `nums[left]` слишком мало даже в паре с самым большим из оставшихся, поэтому оно бесполезно и `left++`. В Trapping Rain Water двигаем сторону с меньшей высотой: уровень воды над ней уже известен, потому что с другой стороны точно есть стенка не ниже.

**`left < right` или `left <= right`.** Вопрос для вывода: что происходит, когда указатели встретились на одном элементе, нужно ли его обработать?

- Нужна пара из двух разных элементов → `left < right`. Один элемент парой не является.
- Каждый элемент надо обработать ровно один раз → `left <= right`. Иначе последний элемент останется необработанным.

Примеры из репозитория:

- [isPalindrome](../src/leetcode/easy/EasySolutions.java) (LC 125) — сравниваем символы с двух концов, не-буквы пропускаем. Средний символ сравнивать не с чем, поэтому хватило бы `<`; в решении стоит `<=`, и это тоже верно: символ просто сравнится сам с собой.
- [trapTwoPointers](../src/leetcode/hard/HardSolutions.java) (LC 42) — здесь `left <= right` обязательно: воду считаем над каждым столбцом, включая тот, на котором указатели встретились.

### 2.2. Указатель чтения и указатель записи

**Сигнал:** «in-place», убрать или сдвинуть элементы, порядок остальных сохранить.

**Смысл указателей:** `read` идёт по всем элементам подряд. `write` — граница готового результата: отрезок `[0, write)` уже в окончательном виде.

```java
int write = 0;
for (int read = 0; read < n; read++) {
    if (элемент нужно оставить) {
        nums[write] = nums[read];
        write++;
    }
}
return write; // длина результата
```

**Откуда берётся путаница с `+1`.** Указатель записи может означать две разные вещи, и от этого зависит весь код:

- `write` — **следующая свободная** позиция. Тогда пишем `nums[write++] = x`, а длина результата равна `write`.
- `write` — **последняя записанная** позиция. Тогда пишем `nums[++write] = x`, а длина результата равна `write + 1`.

В репозитории есть оба варианта рядом:

- [removeDuplicates](../src/leetcode/easy/EasySolutions.java) (LC 26): `j` — последний записанный, поэтому `nums[++j] = nums[i]` и `return j + 1`.
- [removeDuplicatesAllowTwo](../src/leetcode/easy/EasySolutions.java) (LC 80): `j` — следующая свободная, поэтому `nums[j++] = nums[i]` и `return j`. Сравнение с `nums[j - 2]` читается так: «если положить элемент в позицию `j`, станет ли он третьим одинаковым подряд?»

Оба варианта правильные. Ошибка появляется, когда в одном решении они смешаны. Совет: всегда брать «следующую свободную» — тогда `write` одновременно является длиной результата.

- [moveZeroes](../src/leetcode/easy/EasySolutions.java) (LC 283): тот же шаблон, только вместо записи обмен, чтобы нули уехали в конец.

### 2.3. По указателю на каждую последовательность

**Сигнал:** две отсортированные последовательности, или «является ли одна строка подпоследовательностью другой», или жадное сопоставление после сортировки.

**Смысл указателей:** всё, что левее `i` в первой и левее `j` во второй, уже обработано.

```java
int i = 0, j = 0;
while (i < n && j < m) {
    if (a[i] <= b[j]) { взять a[i]; i++; }
    else              { взять b[j]; j++; }
}
// один из массивов мог не закончиться — дообработать хвосты
```

**Условие цикла** выводится из тела: внутри читаются и `a[i]`, и `b[j]`, значит оба индекса должны быть в границах, отсюда `&&`. После цикла один из массивов мог остаться недочитанным — про хвост забывают чаще всего.

Примеры из репозитория:

- [merge](../src/leetcode/easy/EasySolutions.java) (LC 88) — слияние и два цикла для хвостов. Без копии можно, если заполнять `nums1` с конца: тогда запись не затирает ещё не прочитанное.
- [SubselectChecker](../src/ya/algorithm_course/third_sprint_sort/SubselectChecker.java) (≈LC 392) — указатель по тексту идёт всегда, указатель по искомой строке только при совпадении. Ответ: дошёл ли второй указатель до конца.
- [Cookies](../src/ya/algorithm_course/third_sprint_sort/Cookies.java) (≈LC 455) — сортируем оба массива; указатель по печенькам идёт всегда, указатель по детям только когда печенька подошла.

В двух последних задачах один и тот же приём: один указатель двигается безусловно (его удобно сделать переменной `for`), второй — по условию.

### 2.4. Три зоны (голландский флаг)

**Сигнал:** разложить элементы на три группы за один проход и O(1) памяти.

**Смысл указателей** в [sortColors](../src/leetcode/medium/MediumSolutions.java) (LC 75): `[0, low)` — нули, `[low, mid)` — единицы, `[mid, high]` — ещё не просмотрено, `(high, n-1]` — двойки.

Из этого выводится всё остальное:

- Цикл `while (mid <= high)`: непросмотренная зона `[mid, high]` включает `high`, значит при `mid == high` один элемент ещё не проверен.
- После обмена с `high` указатель `mid` не двигаем: оттуда пришёл непроверенный элемент.
- После обмена с `low` указатель `mid` двигаем: из зоны `[low, mid)` могла прийти только единица.

## 3. Скользящее окно

**Сигнал:** непрерывный подмассив или подстрока, нужно найти самый длинный, самый короткий или количество, условие монотонно (см. раздел 1).

**Одно соглашение на все задачи:** окно — это отрезок `[left, right]`, оба конца включительно. Тогда длина окна всегда `right - left + 1`.

**Состояние окна** — то, что позволяет проверить условие за O(1): сумма, множество символов, мапа частот, счётчик нулей. При расширении добавляем в состояние `nums[right]`, при сужении убираем `nums[left]`.

Цикл по `right` всегда `for`: правый край просто идёт слева направо. Левый край двигается во вложенном `while`.

### 3.1. Самое длинное допустимое окно

Расширяем, и если окно испортилось — сужаем, пока не починится. Ответ обновляем **после** `while`: в этот момент окно допустимо и для данного `right` оно максимальное.

```java
int left = 0, best = 0;
for (int right = 0; right < n; right++) {
    добавить(nums[right]);
    while (окноНедопустимо()) {
        убрать(nums[left]);
        left++;
    }
    best = Math.max(best, right - left + 1);
}
```

Пример: [CountUniqueSubstring](../src/ya/algorithm_course/fourth_sprint_hashes/CountUniqueSubstring.java) (≈LC 3), самая длинная подстрока без повторов. Состояние — множество символов окна. В решении проверка стоит до добавления («сужаем, пока новый символ уже есть в окне, потом добавляем») — это тот же шаблон, записанный в другом порядке.

### 3.2. Самое короткое допустимое окно

Расширяем, пока окно не станет допустимым, затем сужаем, пока оно остаётся допустимым. Ответ обновляем **внутри** `while`: каждое окно там допустимо, и каждое следующее короче.

```java
int left = 0, best = Integer.MAX_VALUE;
for (int right = 0; right < n; right++) {
    добавить(nums[right]);
    while (окноДопустимо()) {
        best = Math.min(best, right - left + 1);
        убрать(nums[left]);
        left++;
    }
}
return best == Integer.MAX_VALUE ? 0 : best;
```

Пример: [minSubArrayLen](../src/leetcode/medium/MediumSolutions.java) (LC 209), самый короткий подмассив с суммой ≥ target. Состояние — сумма окна.

**Как не перепутать два шаблона.** Правило одно: ответ обновляется в тот момент, когда окно допустимо.

- Ищем самое длинное → сужаем, пока окно плохое → допустимым оно становится после `while` → обновляем после.
- Ищем самое короткое → сужаем, пока окно хорошее → допустимо оно внутри `while` → обновляем внутри.

### 3.3. Окно фиксированного размера k

```java
int sum = 0;
for (int right = 0; right < n; right++) {
    sum += nums[right];
    if (right >= k) sum -= nums[right - k];   // выпал элемент слева
    if (right >= k - 1) best = Math.max(best, sum); // окно набрало размер k
}
```

Отдельный `left` не нужен: левый край окна всегда `right - k + 1`, а выпавший элемент стоит на позиции `right - k`.

### 3.4. Когда окно не работает

- **В массиве есть отрицательные числа, а условие на сумму.** Сумма перестаёт быть монотонной: сужение окна может её увеличить. Нужны префиксные суммы и хеш-мапа (LC 560; в репозитории — [Contest](../src/ya/algorithm_course/fourth_sprint_hashes/Contest.java), ≈LC 525).
- **Нужна подпоследовательность, а не подстрока.** Элементы можно пропускать, окна нет. Обычно это ДП или жадный алгоритм.
- **«Ровно k» вместо «не больше k».** Условие «ровно» не монотонно. Приём: `ровно(k) = неБольше(k) − неБольше(k − 1)`, а «не больше» уже считается окном.

## 4. Как вывести условие цикла, а не вспоминать его

Четыре шага перед тем, как писать `while`:

1. **Записать смысл указателей одной фразой.** «Окно `[left, right]` включительно». «`[0, write)` — готовый результат». «Всё вне `[left, right]` отброшено».
2. **Посмотреть, какие индексы читаются в теле цикла.** Условие обязано гарантировать, что все они в границах. Если в теле есть `nums[right + 1]`, в условии будет `right + 1 < n`. Если читаются `a[i]` и `b[j]`, в условии будет `i < n && j < m`. Выражение вида `right + 1` появляется в условии только потому, что код заглядывает на элемент вперёд.
3. **Спросить, что происходит при встрече указателей.** Один элемент между ними — это ещё работа или уже конец? Если работа, то `<=`, если конец, то `<`.
4. **Проверить руками на массиве из одного и из двух элементов.** Ошибки на единицу проявляются именно там.

Условие внутреннего `while` в окне — это не про индексы, а про состояние: «окно недопустимо» или «окно допустимо». Его формулируем словами из условия задачи (сумма ≥ target, символ уже есть в множестве) и не привязываем к `left` и `right` вообще.

## 5. С чем не путать

| Задача выглядит как | Но на самом деле | Как отличить |
|---|---|---|
| Окно: «подмассив с суммой k» | префиксные суммы + мапа | есть отрицательные числа или нужно «ровно k» |
| Окно: «самая длинная …» | ДП | речь о подпоследовательности, элементы можно пропускать |
| Два указателя: «найти пару с суммой» | хеш-мапа ([twoSum](../src/leetcode/easy/EasySolutions.java), LC 1) | массив не отсортирован и нужны индексы, а сортировка их потеряет |
| ДП: «максимальная прибыль», «минимальная длина» | окно или один проход | ответ — непрерывный отрезок, и состояние окна пересчитывается за O(1) |
| Два указателя навстречу | бинарный поиск | ищем не пару, а одно значение или границу |

Про ДП отдельно: если хочется решать динамикой, сначала стоит спросить себя — ответ здесь непрерывный отрезок? Если да, скорее всего достаточно окна или двух указателей, и решение получится за O(n) времени и O(1) памяти.
